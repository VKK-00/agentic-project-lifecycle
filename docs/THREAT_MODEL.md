# Agentic Project Lifecycle Threat Model

## Scope and security objective

Agentic Project Lifecycle is a local governance and evidence control plane for agent-assisted software work. It does not grant model, filesystem, network, GitHub, deployment, or production authority. Its security objective is to ensure that consequential work is bounded by an approved contract, that mechanically verifiable claims are checked deterministically, and that readiness decisions remain traceable to fresh evidence for an exact source state.

The primary assets are approved requirements and plans, repository source and history, credentials and private data, governance policy, approvals and waivers, evidence artifacts, release decisions, and the integrity of the execution trace. Trust boundaries exist between higher-level policy and repository content; planner, executor, and verifier roles; the repository and external tools or MCP servers; local workspaces and network services; and generated evidence and the human or system that consumes it.

## Threat actors and assumptions

Threats may originate from malicious repository content, compromised dependencies or tools, an over-privileged or misconfigured agent, indirect prompt injection from fetched material, a dishonest or mistaken contributor, tampered evidence, or a compromised CI identity. Model output, repository prose, comments, issues, fixtures, tool output, and externally fetched content are untrusted until a trusted policy or deterministic validator establishes a narrower claim.

## Threat register

| Threat | Asset | Attacker and attack path | Required controls | Residual risk |
|---|---|---|---|---|
| **Goal hijacking** | Approved objective and task boundary | A README, issue, retrieved document, or tool response tells the agent to replace the approved goal, skip gates, or perform unrelated work. | Context packets label project content untrusted; task and policy digests bind execution; actual-diff validation rejects scope expansion; higher-level instructions cannot be overridden by repository prose. | A model may still waste analysis effort or misclassify ambiguous content before deterministic enforcement runs. |
| **Tool misuse** | Repository, network services, and external systems | An agent invokes an allowed tool with unsafe arguments, composes commands to bypass a deny rule, or uses a verification command for mutation. | Least-privilege permissions, argument-vector execution, command allowlists, protected surfaces, source/tree/branch invariance, post-command diff checks, and explicit approval for elevated permissions. | Command semantics can be complex; provider sandboxes and OS controls remain necessary defense layers. |
| **Identity and privilege abuse** | Approvals, GitHub permissions, and deployment authority | A model writes `approved_by`, impersonates a reviewer, reuses stale approval, or escalates network/dependency/destructive permissions. | Source-bound approvals, assurance levels, policy-required roles, stale-approval invalidation, branch protection, CODEOWNERS, and separation between proposer, verifier, and merger. | Local declared approvals do not prove external identity unless backed by signed Git or GitHub review evidence. |
| **Agentic supply chain** | Skills, dependencies, actions, models, MCP servers, and release artifacts | A dependency lifecycle script, compromised Action, malicious skill, model alias, or MCP server injects code or instructions. | Pinned versions and action SHAs, dependency review, SBOM, provenance attestations, trusted skill sources, model snapshot recording, no network by default, and hostile-fixture evaluation. | Upstream compromise and model-service behavior cannot be fully eliminated; provenance establishes origin, not safety. |
| **Unexpected code execution** | Host and repository integrity | Package hooks, shell metacharacters, malicious test configuration, Git hooks, or fetched scripts execute outside the intended command. | No implicit shell for verification commands, disposable worktrees, disabled network, restricted writable roots, hook-neutral Git operations, command policy, timeouts, and post-execution state comparison. | Language runtimes and test tools may execute project code by design; isolated environments are still required for hostile repositories. |
| **Evidence fabrication** | Readiness and release decisions | An agent invents a passing result, edits both a log and its digest, copies stale evidence, or reports another commit's results. | Tool-observed exit codes, exact source binding, immutable run directories, artifact digests, hash-chained events, freshness windows, report digesting, and cross-contract audit. | A compromised collector or host can fabricate internally consistent evidence; signed external provenance raises assurance. |
| **Approval bypass** | Consequential decisions | Work begins before approval, a required role is omitted, a phase is skipped, or a waiver is treated as approval. | Typed transition semantics, versioned policy profiles, required-role coverage, non-waivable blocker classes, exact task confirmation, and fail-closed gates. | Human reviewers can still make poor decisions; the system records and bounds rather than replaces judgment. |
| **Memory poisoning** | Durable project state and future agent context | False facts, malicious summaries, or obsolete decisions are persisted as canonical project memory and reused later. | One canonical source per fact or decision, stable IDs, source hashes, explicit fact/assumption separation, freshness and supersession metadata, bounded context packs, and reopening gates when evidence changes. | Semantic truth cannot be proven mechanically in all cases; independent review remains necessary for consequential claims. |
| Symlink and path escape | Filesystem boundary and secrets | A repository path or artifact resolves outside the project root, including Windows path variants or nested symlinks. | Repository-relative normalized paths, traversal rejection, component-by-component symlink rejection, resolved-root containment, sensitive-path denylist, and adversarial tests. | Platform-specific filesystem behavior may create edge cases; CI must cover supported platforms. |
| Denial of service and resource exhaustion | Availability and evaluation budget | Huge files, deeply nested YAML, infinite tools, repeated retries, or oversized context exhaust time, memory, or tokens. | File/byte/diff budgets, command timeouts, iteration limits, bounded parsing, atomic publication, cancellation, and explicit incomplete status. | Legitimate large projects may require reviewed budget increases. |
| Trace or policy tampering | Audit history and governance rules | An actor edits the task, policy, run log, or validator after approval and presents the result as unchanged. | Contract and policy digests, immutable event chain, source commit binding, protected paths, signed commits, required reviews, and release provenance. | Administrators with repository and CI control can rewrite history unless external transparency or signed attestations are used. |

## Security invariants

1. Repository and external content cannot enlarge permissions, enable network access, weaken verification, alter approval policy, or authorize production actions.
2. Write-capable execution requires an approved source-bound task contract and a rollback checkpoint.
3. An open hard blocker stops dependent work; a waiver is explicit, scoped, owned, expiring, and never converts failed evidence into passing evidence.
4. Verification evidence is valid only for the recorded source commit, environment, command, artifacts, and freshness window.
5. The actual Git diff must conform to approved paths, budgets, dependency policy, protected-surface rules, and execution lineage.
6. Planner and verifier stages are read-only; an executor cannot approve or independently verify its own work.
7. Missing, malformed, stale, or unverifiable data is a visible gap and causes a fail-closed decision.

## Validation and response

Each threat maps to deterministic unit or adversarial fixture tests where mechanics are observable, and to repeated live behavioral evaluations where model judgment is involved. A detected violation produces a stable issue code, blocks the affected gate, preserves the failed diff or trace when safe, and requires a new source-bound plan or explicit risk decision. Security-sensitive findings are not silently downgraded or waived by the agent that produced them.
